# AIDC 产业链研究 — 季度证据刷新机制

## 1. 机制概述

本机制为 AIDC 产业链研究案例 (case_id: aidc-supply-chain-20260630) 建立制度化的季度证据刷新流程，确保 59 家候选公司的字段证据矩阵在每次财报季和重大事件后得到及时更新，维持研究结论的时效性和准确性。

**当前基线** (2026-07-01):
- 候选公司: 59 家
- 字段总数: 413 (59 x 7)
- 证据状态: direct 409 / proxy 2 / broker_indirect 2
- 残余代理字段: 603881 数据港 (产能/认证)、002334 英威腾 (利用率/良率/爬坡)
- 观察名单公司: 300936 中英科技、603912 佳力图、002334 英威腾
- 来源耗尽状态: complete_with_public_corpus_gaps

## 2. 触发条件

### 2.1 定期触发 (财报季后)

| 触发窗口 | 财报类型 | 截止日期 | 刷新启动 |
|----------|---------|---------|---------|
| 4月下旬 | 年报 (上年度) | 4月30日 | 5月5日前完成 |
| 8月下旬 | 半年报 | 8月31日 | 9月5日前完成 |
| 10月下旬 | 三季报 | 10月31日 | 11月5日前完成 |

### 2.2 事件驱动触发

| 事件类型 | 判定标准 | 响应时间 |
|---------|---------|---------|
| 重大行业事件 | 头部云厂商资本开支调整 >20%、AI 服务器出货量预期修正 >15%、光模块/液冷/电源等关键环节技术突破 | 48小时内启动专项刷新 |
| 政策变化 | 数据中心能耗标准修订、AI 算力基础设施政策、运营商集采规则变化 | 72小时内启动专项刷新 |
| 公司重大公告 | 单笔 AIDC 相关订单 >1亿元、核心客户认证通过、产能扩张 >30%、核心技术人员变动 | 24小时内启动单公司刷新 |
| 券商首次覆盖 | 观察名单公司获得首次券商覆盖并含目标价 | 48小时内评估升级条件 |

### 2.3 手动触发

研究团队任何成员可通过提交刷新请求手动触发，需注明:
- 触发原因
- 涉及公司/字段范围
- 紧急程度 (常规/加急)

## 3. 刷新流程

### 3.1 标准季度刷新 (SOP)

```
阶段 1: 准备 (T-3 至 T-1)
  ├─ 拉取当前字段证据完成矩阵 (field_evidence_completion_*.json)
  ├─ 拉取当前残余代理字段审计 (residual_proxy_field_audit_*.json)
  ├─ 拉取观察名单升级触发器状态 (watchlist_valuation_triggers.json)
  ├─ 拉取来源耗尽日志 (source_exhaustion_log.md)
  └─ 生成本轮刷新任务清单

阶段 2: 证据采集 (T 至 T+3)
  ├─ 2.1 财报数据采集 (所有 59 家)
  │   ├─ 最新年报/半年报/季报 (CNINFO)
  │   ├─ 投资者关系活动记录 (交易所 IR 平台)
  │   └─ 业绩说明会纪要
  ├─ 2.2 券商报告采集 (所有 59 家)
  │   ├─ 新增券商研报 (东方财富/同花顺/iFind)
  │   ├─ 重点关注: 首次覆盖、目标价大幅调整 (>20%)
  │   └─ 5 家无公开券商 PDF 公司的覆盖进展
  ├─ 2.3 官方公告采集 (所有 59 家)
  │   ├─ 中标公告
  │   ├─ 重大合同公告
  │   ├─ 产能/认证进展公告
  │   └─ 投资者关系活动记录表
  └─ 2.4 代理字段专项采集 (仅 2 家残余代理字段)
      ├─ 603881 数据港: 产能/认证字段升级检查
      └─ 002334 英威腾: 利用率/良率/爬坡字段升级检查

阶段 3: 字段重分类 (T+3 至 T+4)
  ├─ 3.1 代理字段 → direct 升级判定
  │   ├─ 检查是否有新的直接证据覆盖原代理字段
  │   ├─ 评估证据质量 (来源权威性、量化程度、时效性)
  │   └─ 满足条件则升级为 direct
  ├─ 3.2 broker_indirect → direct 升级判定
  │   ├─ 检查是否有公司官方披露替代券商间接证据
  │   └─ 满足条件则升级为 direct
  ├─ 3.3 direct 字段证据更新
  │   ├─ 用最新财报/公告更新证据片段
  │   ├─ 更新 source 路径和 score
  │   └─ 记录变化前后对比
  └─ 3.4 观察名单公司升级评估
      ├─ 检查 U1-U5 升级触发器是否满足
      ├─ 计算综合差距评分变化
      └─ 生成升级/维持/降级建议

阶段 4: 矩阵更新 (T+4 至 T+5)
  ├─ 4.1 更新字段证据完成矩阵
  ├─ 4.2 更新残余代理字段审计 (如有变化)
  ├─ 4.3 更新来源耗尽日志
  ├─ 4.4 生成证据变化报告
  └─ 4.5 更新 field_evidence_completion_audit.md

阶段 5: 治理审查 (T+5)
  ├─ 5.1 变化超过 5 个字段 → 触发 R0 审查
  ├─ 5.2 观察名单公司满足升级条件 → 触发 R1 审查
  ├─ 5.3 代理字段升级 → 记录到 skill_evolution_log
  └─ 5.4 运行验证器 (39 PASS / 0 FAIL 要求)
```

### 3.2 事件驱动专项刷新 (简化流程)

```
事件识别 → 范围界定 (单公司/单字段/全行业) → 定向证据采集 → 字段重分类 → 矩阵更新 → 治理审查
```

响应时间要求:
- 单公司事件: 24 小时内完成
- 行业/政策事件: 72 小时内完成

## 4. 检查清单 (每家公司)

### 4.1 财报披露检查

- [ ] 最新财报中的 AIDC 相关收入披露 (分产品/分业务收入)
- [ ] 最新财报中的 AIDC 相关毛利率披露
- [ ] 最新财报中的产能/在建工程/资本开支信息
- [ ] 最新财报中的研发投入及方向

### 4.2 投资者关系检查

- [ ] 最新投资者关系活动记录中的订单信息
- [ ] 最新投资者关系活动记录中的客户信息 (是否有新 AI 客户)
- [ ] 最新投资者关系活动记录中的产能/产能利用率信息
- [ ] 最新投资者关系活动记录中的 ASP/价格变化信息
- [ ] 最新投资者关系活动记录中的良率/稼动率信息

### 4.3 券商报告检查

- [ ] 新发布的券商研报 (自上次刷新以来)
- [ ] 首次覆盖情况 (特别是观察名单公司)
- [ ] 目标价调整 (变化 >20% 需标注)
- [ ] 盈利预测调整 (收入/净利润/EPS)
- [ ] 评级变化 (买入/增持/中性/减持)

### 4.4 官方公告检查

- [ ] 新的中标公告 (金额 >5000 万元)
- [ ] 新的重大合同公告 (金额 >1 亿元)
- [ ] 产能扩张公告
- [ ] 客户认证进展公告
- [ ] 核心技术/产品认证公告

### 4.5 运营指标检查

- [ ] 产能/认证进展 (新产线投产、认证通过)
- [ ] ASP/价格变化信息 (提价/降价、产品结构变化)
- [ ] 利用率/良率/稼动率更新
- [ ] 毛利率/净利率变化 (环比、同比)

### 4.6 代理字段专项检查 (仅适用公司)

| 公司 | 字段 | 升级条件 | 优先级 |
|------|------|---------|--------|
| 603881 数据港 | 产能/认证 | 年报/半年报中披露独立产能明细或认证进展；IR 中提及具体机柜/MW 利用率 | 高 |
| 002334 英威腾 | 利用率/良率/爬坡 | 季报中披露网络能源业务稼动率；IR 中提及 UPS/液冷产能利用率 | 高 |

## 5. 自动化脚本设计

### 5.1 脚本规格

| 项目 | 说明 |
|------|------|
| 脚本名称 | `refresh_evidence_quarterly.py` |
| 位置 | `improvements/refresh_evidence_quarterly.py` |
| 语言 | Python 3.9+ |
| 依赖 | json, os, datetime, pathlib, csv, re |

### 5.2 输入

| 输入 | 来源 | 格式 |
|------|------|------|
| 当前字段证据矩阵 | `data/field_evidence_completion_*.json` (最新) | JSON |
| 残余代理字段审计 | `data/residual_proxy_field_audit_*.json` (最新) | JSON |
| 新财报数据 | `sources/` 目录下新归档文件 | 文本/PDF |
| 新券商报告 | `sources/broker-reports/` 新归档 | Markdown/文本 |
| 观察名单触发器 | `improvements/watchlist_valuation_triggers.json` | JSON |
| 来源耗尽日志 | `source_exhaustion_log.md` | Markdown |

### 5.3 输出

| 输出 | 位置 | 格式 |
|------|------|------|
| 更新后的字段证据矩阵 | `data/field_evidence_completion_YYYYMMDD.json` | JSON |
| 证据变化日志 | `data/evidence_refresh_delta_YYYYMMDD.json` | JSON |
| 证据变化报告 (可读) | `analysis/field_evidence_refresh_report_YYYYMMDD.md` | Markdown |
| 代理字段升级建议 | `improvements/proxy_upgrade_candidates_YYYYMMDD.json` | JSON |
| 观察名单升级评估 | `improvements/watchlist_upgrade_assessment_YYYYMMDD.json` | JSON |
| 刷新执行摘要 | `improvements/refresh_summary_YYYYMMDD.md` | Markdown |

### 5.4 关键功能模块

1. **字段状态检测模块** (`detect_field_status_changes`)
   - 对比新旧矩阵，识别状态变化 (proxy→direct, broker_indirect→direct)
   - 检测 direct 字段的证据更新 (新来源、新片段)

2. **代理字段升级检测模块** (`check_proxy_upgrade_opportunities`)
   - 针对残余代理字段，在新来源中搜索直接证据
   - 评估证据质量 (来源类型、量化程度、时效性)
   - 生成升级建议 (含置信度评分)

3. **观察名单升级检测模块** (`check_watchlist_upgrade_conditions`)
   - 检查 U1-U5 触发器是否满足
   - 计算综合差距评分变化
   - 生成升级/维持/降级建议

4. **变化报告生成模块** (`generate_change_report`)
   - 统计字段变化数量
   - 生成变化前后对比表
   - 标注需要 R0/R1 审查的变化

5. **治理合规检查模块** (`check_governance_compliance`)
   - 检查变化数量是否触发 R0 审查 (>5 字段)
   - 检查观察名单升级是否触发 R1 审查
   - 验证所有变化是否有对应来源支持

## 6. 治理要求

### 6.1 刷新后必做更新

| 更新项 | 文件 | 条件 |
|--------|------|------|
| 字段证据完成审计 | `analysis/field_evidence_completion_audit.md` | 每次刷新后 |
| 残余代理字段审计 | `data/residual_proxy_field_audit_*.json` | 代理字段状态变化时 |
| 来源耗尽日志 | `source_exhaustion_log.md` | 有新来源归档或来源状态变化时 |
| 审查日志 | `review_log.md` | 触发 R0/R1 审查时 |
| 技能进化日志 | `skill_evolution_log.json` | 代理字段升级或流程改进时 |

### 6.2 审查触发规则

| 触发条件 | 审查级别 | 审查内容 | 负责人 |
|---------|---------|---------|--------|
| 字段变化 >5 个 | R0 证据审查 | 新证据的来源可靠性、证据质量、字段分类准确性 | 研究负责人 |
| 观察名单公司满足升级条件 | R1 模型审查 | 升级后的模型适用性、估值参数、目标价合理性 | 估值分析师 |
| 代理字段升级为 direct | 记录 | 在 skill_evolution_log 中记录升级路径和证据来源 | 刷新执行人 |
| 新增无来源公司 | R0 证据审查 | 评估是否需要启动新的来源采集 | 研究负责人 |

### 6.3 验证器要求

每次刷新并更新相关文件后，**必须**运行:

```bash
# 案例级验证 (39 PASS / 0 FAIL)
python3 tools/verify_research_workspace.py

# 工作流门控 (RESULT PASS)
python3 workspace/research/tools/run_research_gates.py <case-dir>
```

**未通过验证器的刷新结果不得发布。**

### 6.4 刷新依赖链 (Section 6-7 合规)

刷新执行后，必须按以下顺序完成依赖刷新，验证器才会通过:

```
1. PDF 重建清理 (latexmk -c)
2. 治理文件 .md → .json 同步
3. 核心工件校验和重算 (core_artifact_checksums)
4. 顶层数据工件清单刷新至固定点 (top_level_data_artifact_inventory)
5. 报告质量评估 (report_quality_eval)
6. 完成审计清单更新 (completion_audit_manifest)
```

跳过任何刷新依赖步骤导致的验证器 FAIL 本身即为 A 级流程发现。

## 7. 角色与职责

| 角色 | 职责 |
|------|------|
| 刷新执行人 | 执行季度刷新 SOP，运行脚本，更新矩阵 |
| 证据审核人 | 审核新证据的来源可靠性和字段分类准确性 |
| R0 审查人 | 审查字段变化 >5 的刷新结果 |
| R1 审查人 | 审查观察名单公司升级建议 |
| 研究负责人 | 最终审批刷新结果，签署发布 |

## 8. 质量指标

每次刷新后记录以下指标，用于趋势分析:

| 指标 | 计算方式 | 目标 |
|------|---------|------|
| 字段证据直接率 | direct 字段数 / 总字段数 | >98% |
| 代理字段数 | proxy + broker_indirect 字段数 | <4 |
| 观察名单公司数 | watchlist_only 状态公司数 | <5 |
| 刷新字段变化率 | 本次变化字段数 / 总字段数 | <15% |
| 新来源归档数 | 本次刷新新增的来源文件数 | 持续增长 |
| 验证器通过率 | PASS 数 / 总检查数 | 100% (39/39) |
| 刷新完成时效 | 从财报截止到刷新完成的天数 | <5 天 |
